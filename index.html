Architecture & Internals
01
COREARCHITECTURE
Explain Frappe's request lifecycle — from HTTP request to response. Where does the ORM, permission check, and controller hook each fit in?
▾
Answer

Full lifecycle: Nginx → Gunicorn (Python WSGI) → frappe.app (WSGI handler) → frappe.handler.handle() → method routing via frappe.get_doc / frappe.call → ORM → DB.

Permission check fires inside frappe.get_doc() before any data hits Python — via has_permission() which reads DocPerm + User Permission records.

Controller hooks fire at document lifecycle stages: before_insert → validate → on_submit → on_cancel. These run inside the same DB transaction, so raising an exception rolls back cleanly.

Key insight: Frappe uses a single MariaDB connection per request (stored in frappe.db), which means long-running hooks can hold locks — a common production issue.

Mention RQ workers for async jobs — background tasks bypass this lifecycle entirely via Redis queues.
02
COREDOCTYPE
What is the difference between a frappe.get_doc(), frappe.get_cached_doc(), and frappe.get_last_doc()? When would each cause a bug in production?
▾
Answer

get_doc() — always hits the DB. Safe, fresh, but slower in loops.

get_cached_doc() — reads from Redis cache first. Dangerous if you mutate a cached doc (e.g., in a background job) and expect live data — cache may be stale for up to the TTL window.

get_last_doc() — fetches newest record by creation desc. Bug risk: in high-concurrency inserts (e.g., bulk onboarding), you may get a different user's record if the query runs between two concurrent inserts.

Production bug scenario: Using get_cached_doc inside a scheduler job on a setting DocType where an admin just updated a value — the job reads stale config for up to 10 minutes.

Always call frappe.clear_cache(doctype, name) after programmatic updates to single-record DocTypes like settings.
03
COREARCHITECTURE
How does Frappe's multi-tenancy (bench sites) work at the DB and file level? How do you handle cross-site data sharing?
▾
Answer

Each site has its own MariaDB database, its own site_config.json, and its own private/public file directories. There is no shared DB between sites.

Redis is shared across sites by default but namespaced by site name in cache keys.

Cross-site data sharing options:

1. Frappe's REST API — sites call each other via HTTP with API token auth. Fragile but simple.

2. Shared MariaDB views — create a read-only DB user with SELECT access to another site's DB and use frappe.db.sql() with explicit DB prefix. Risky — bypasses all Frappe ORM/permissions.

3. Message broker (Redis pub/sub or RabbitMQ) — emit events from site A, consume in site B's worker. Best for async sync.

Hooks, Events & Customization
04
COREHOOKS
What is the execution order of hooks.py doc_events vs a Controller method override? Which one survives a bench update?
▾
Answer

Execution order for a before_save event:

1. Controller class method (e.g., SalesOrder.before_save() in ERPNext source)

2. doc_events hooks from custom apps (in app installation order from apps.txt)

3. Server Script (if any)

Survival after bench update: Controller method overrides in hooks.py doc_events live in your custom app, so they survive ERPNext updates. Directly patching ERPNext's controller file will be overwritten on bench update.

Gotcha: If two custom apps both hook the same event, order depends on apps.txt — this is a common conflict source in multi-app setups.

Always use doc_events in your custom app's hooks.py — never modify ERPNext source directly.

▾

▾

Scheduler, Background Jobs & Workers
07
CORESCHEDULER
How does Frappe's scheduler work internally? How do you prevent a scheduler job from running concurrently if the previous execution hasn't finished?
▾
Answer

Internals: Frappe uses rq-scheduler — a cron-like scheduler that enqueues jobs into Redis queues at configured intervals. Workers (RQ workers) pick up jobs. The beat process (bench schedule) is the cron tick.

Problem: If a scheduled job takes longer than its interval, RQ will enqueue it again while the previous one is still running, causing concurrent execution and potential data corruption.

Solution — Advisory Lock pattern:

def my_scheduled_job():
    lock_key = "my_job_lock"
    # Try to acquire lock (expires in 10 min)
    if frappe.cache().get(lock_key):
        return  # already running, skip
    
    frappe.cache().set(lock_key, 1, ex=600)
    try:
        # actual job logic here
        process_records()
    finally:
        frappe.cache().delete_key(lock_key)

Use Redis SET NX EX via frappe.cache().set_value() for atomic lock acquisition in distributed setups.

08
SCENARIOBACKGROUND
Scenario: enqueue() jobs are silently failing in production. Workers seem healthy. How do you trace and fix this?
▾
Answer

Silent failures in RQ workers happen for these reasons:

1. Exception swallowed: The job function has a bare except block. Check worker logs: bench logs worker.

2. Job timeout: Default RQ job timeout is 300s. If your job runs longer, it's killed silently. Fix: frappe.enqueue(..., timeout=1800)

3. Queue name mismatch: Job enqueued to long queue but no worker is listening on long. Check Procfile — ensure worker_long is running.

4. Redis memory full: Jobs are dropped. Monitor Redis with redis-cli INFO memory.

5. Failed jobs in RQ: Run bench execute frappe.utils.background_jobs.get_jobs or inspect via rq info.

# Best practice: always wrap job logic
def my_job(doc_name):
    try:
        doc = frappe.get_doc("MyDocType", doc_name)
        # logic
        frappe.db.commit()
    except Exception:
        frappe.log_error(frappe.get_traceback(), "my_job failed")
Performance & Database
09
COREPERFORMANCE
What causes N+1 query problems in Frappe, and how do you identify and fix them in production?
▾
Answer

Common N+1 patterns in Frappe:

1. Calling frappe.get_doc() inside a loop over a list fetched by frappe.get_list().

2. Accessing doc.get_all_children() inside a loop.

3. Using frappe.db.get_value() inside a Jinja template loop.

Identification: Enable SQL query logging — set logging.level = debug in site_config and watch frappe.log, or use frappe.db.sql_count in dev.

Fix:

# WRONG — N+1
invoices = frappe.get_list("Sales Invoice", fields=["name"])
for inv in invoices:
    doc = frappe.get_doc("Sales Invoice", inv.name)  # N queries

# CORRECT — fetch all needed fields in one query
invoices = frappe.get_list("Sales Invoice",
    fields=["name", "customer", "grand_total", "status"])

For aggregations, always use frappe.db.sql() with proper JOINs instead of Python-side aggregation.

10
SCENARIOPERFORMANCE
Scenario: A custom Report is timing out for clients with 500k+ records. Walk through your exact optimization approach.
▾
Answer

Step-by-step approach:

1. EXPLAIN the query — run EXPLAIN SELECT ... in MariaDB. Look for type: ALL (full table scan) — that's your bottleneck.

2. Add custom indexes — Frappe lets you add indexes via DocType's "Search Index" field flag, or directly via migration:

# In a patch file
frappe.db.add_index("tabSales Invoice",
    ["posting_date", "company", "status"])

3. Switch to Script Report with raw SQL — Report Builder is slow for complex queries. Raw SQL with proper JOINs and WHERE clauses beats ORM for reporting.

4. Add pagination — never return all 500k rows. Use LIMIT/OFFSET or cursor-based pagination.

5. Cache results — for reports that run every few minutes with same params, cache output in Redis with a 5-min TTL.

6. Background Report — for very heavy reports, use Frappe's built-in async report feature to run in background and notify user when ready.

11
COREDATABASE
Explain frappe.db.commit() vs frappe.db.savepoint(). When would using commit inside a loop cause a production disaster?
▾
Answer

frappe.db.commit() — flushes the entire transaction to disk. All pending inserts/updates are committed. Releases locks.

frappe.db.savepoint(name) — creates a rollback point within the current transaction. If something fails after, you can roll back to this point without losing earlier work.

Disaster scenario: Processing 1000 invoices in a loop with commit() after each. If the job fails at record 600:

→ Records 1–599 are permanently committed.

→ Records 600–1000 were never written.

→ Your data is now in a half-committed, inconsistent state with no clean rollback.

Better pattern:

for i, row in enumerate(records):
    try:
        frappe.db.savepoint(f"sp_{i}")
        process(row)
    except Exception:
        frappe.db.rollback(save_point=f"sp_{i}")
        frappe.log_error(...)
# Single commit at the end
frappe.db.commit()
Security & Permissions
12
COREPERMISSIONS
Explain the difference between Role Permissions, User Permissions, and Permission Query Conditions. Which one is enforced at SQL level?
▾
Answer

Role Permissions (DocPerm): Define CRUD access at DocType level for a Role. E.g., "Sales User can Read+Write Sales Order." This is a coarse-grained gate.

User Permissions: Row-level restrictions. E.g., "User X can only see Sales Orders where Company = 'Acme'." Stored in tabUser Permission. Frappe filters list views and get_doc based on these.

Permission Query Conditions: A Python function in hooks.py that dynamically appends a WHERE clause to every query for a DocType. Enforced at SQL level — it's injected directly into the SELECT query.

# hooks.py
permission_query_conditions = {
    "Sales Order": "myapp.permissions.get_permission_query"
}

# myapp/permissions.py
def get_permission_query(user):
    if not user: user = frappe.session.user
    if "Sales Manager" in frappe.get_roles(user):
        return ""  # no restriction
    return f"(`tabSales Order`.owner = '{user}')"

Key distinction: User Permissions are evaluated in Python and can be bypassed by raw frappe.db.sql(). Permission Query Conditions are injected into ALL ORM queries — much harder to accidentally bypass.

13
SCENARIOSECURITY
Scenario: A whitelisted API endpoint is leaking data from other companies in a multi-company setup. What went wrong and how do you fix it?
▾
Answer

What went wrong:

1. The @frappe.whitelist() function is using raw frappe.db.sql() or frappe.db.get_all() without a company filter — bypassing User Permissions entirely.

2. No has_permission() check on returned documents.

Fix:

@frappe.whitelist()
def get_my_invoices():
    user = frappe.session.user
    
    # 1. Validate user's allowed companies
    allowed_companies = frappe.get_list("User Permission",
        filters={"user": user, "allow": "Company"},
        fields=["for_value"],
        ignore_permissions=True
    )
    company_list = [c.for_value for c in allowed_companies]
    
    if not company_list:
        frappe.throw("No company access", frappe.PermissionError)
    
    # 2. Filter at query level
    return frappe.get_list("Sales Invoice",
        filters={"company": ["in", company_list]},
        fields=["name", "customer", "grand_total"]
    )

Best practice: Never return raw DB results from a whitelisted method without explicit permission/company scoping.

Custom Apps & DocType Design
14
COREDESIGN
When do you use a Child Table DocType vs a Link field vs a Dynamic Link? What are the trade-offs for querying and reporting?
▾
Answer

Child Table: Use when you need multiple rows of the same structure owned by a parent (e.g., Invoice Items). Stored in a separate DB table (tabSales Invoice Item). The parent-child relationship is tight — child rows are deleted when parent is deleted.

Link field: A foreign key to a specific DocType. Type-safe, indexable, can be used in standard filters. Best for relationships like Sales Order → Customer.

Dynamic Link: A combination of a link_doctype selector field + a value field that stores the linked document name. Flexible but cannot be indexed efficiently — bad for reporting. Use only when the linked DocType is truly variable (e.g., a Comments model that links to any DocType).

Query trade-offs: Dynamic Links require runtime JOIN with the link_doctype field resolved — can't create a static index. This makes list view filters on dynamic links very slow at scale.

For reporting-heavy use cases, always prefer Link over Dynamic Link. Add a DB index on frequently filtered Link fields.
15
SCENARIOMIGRATION
Scenario: You need to rename a custom field that is used in filters, reports, and client scripts across the app — without breaking production. What's your migration strategy?
▾
Answer

Never just rename a field in the DocType JSON — it drops the column and re-creates it, losing all data.

Safe strategy:

1. Add the new field alongside the old one (don't remove old yet).

2. Write a patch to copy data from old → new field:

# In patches/migrate_field.py
def execute():
    frappe.db.sql("""
        UPDATE `tabMyDocType`
        SET `new_field` = `old_field`
        WHERE `old_field` IS NOT NULL
    """)
    frappe.db.commit()

3. Update all references — server scripts, client scripts, report columns, custom filters, Jinja templates.

4. Mark old field as hidden (not deleted) and deploy. Monitor for a sprint.

5. Delete old field in the next release after confirming nothing references it.

Tools: Use bench grep "old_field_name" across your app codebase before step 3.

COREVERSIONING
What is Frappe's Document Versioning mechanism? How do you implement selective field-level audit trails for sensitive data?
▾
Answer

Frappe's built-in versioning: Enable "Track Changes" on a DocType — Frappe stores a JSON diff in the Version DocType after each save. Accessible via the document's "Version" tab in UI.

Limitation: It tracks all fields — can be noisy, stores large JSON blobs, and is not queryable for specific field values.

Custom field-level audit trail:

# hooks.py
doc_events = {
    "Customer": {
        "on_update": "myapp.audit.log_sensitive_changes"
    }
}

# myapp/audit.py
SENSITIVE_FIELDS = ["pan_number", "credit_limit", "tax_id"]

def log_sensitive_changes(doc, method):
    old = doc.get_doc_before_save()
    if not old:
        return
    for field in SENSITIVE_FIELDS:
        if doc.get(field) != old.get(field):
            frappe.get_doc({
                "doctype": "Audit Log",
                "document_type": doc.doctype,
                "document_name": doc.name,
                "field": field,
                "old_value": old.get(field),
                "new_value": doc.get(field),
                "changed_by": frappe.session.user
            }).insert(ignore_permissions=True)
Frontend, Client Scripts & Forms
17
COREFRONTEND
What is the difference between frappe.ui.form.on event handlers and setup vs refresh vs onload? When does each fire?
▾
Answer

onload: Fires once when the form is first loaded into the DOM. Use for one-time setup that shouldn't repeat (e.g., setting a field default programmatically based on URL param). Does NOT fire on every refresh.

setup: Fires once after the form controller is instantiated. Use for binding event listeners to fields or setting up formatters. Also fires only once per form lifetime in the browser.

refresh: Fires every time the form is rendered or re-rendered — on load, after save, after route change back to same doc. Use for showing/hiding fields, adding custom buttons, updating UI state based on doc status. This is the most commonly used hook.

frappe.ui.form.on("Sales Order", {
    setup: function(frm) {
        // One-time: set query filter for a Link field
        frm.set_query("territory", () => ({
            filters: { is_active: 1 }
        }));
    },
    refresh: function(frm) {
        // Every render: show/hide button based on status
        frm.toggle_display("approve_btn",
            frm.doc.status === "Pending Approval");
    },
    onload: function(frm) {
        // Once: prefill from URL params
        const ref = frappe.utils.get_url_arg("ref");
        if (ref) frm.set_value("reference", ref);
    }
});

SCENARIOFRONTEND
Scenario: A frappe.call() in a client script causes a race condition — users rapidly clicking "Approve" submit the form twice. How do you prevent it?
▾
Answer

Client-side prevention:

let is_submitting = false;

frappe.ui.form.on("Loan Application", {
    refresh(frm) {
        frm.add_custom_button("Approve", function() {
            if (is_submitting) return; // guard
            is_submitting = true;
            frm.disable_save(); // prevent any other save

            frappe.call({
                method: "myapp.api.approve_loan",
                args: { name: frm.doc.name },
                callback(r) {
                    is_submitting = false;
                    frm.enable_save();
                    frm.reload_doc();
                },
                error() {
                    is_submitting = false;
                    frm.enable_save();
                }
            });
        });
    }
});

Server-side guard (critical): Always check document status server-side — the client guard is for UX only, not security:

@frappe.whitelist()
def approve_loan(name):
    doc = frappe.get_doc("Loan Application", name)
    if doc.status != "Pending":
        frappe.throw("Already processed")
    # proceed
ERPNext Domain-Specific
19
COREACCOUNTING
Explain how ERPNext's double-entry accounting is enforced at code level. What prevents a GL Entry from being imbalanced?
▾
Answer

Mechanism: ERPNext calls make_gl_entries() in the accounting controller, which generates a list of GL Entry dicts. Before inserting, it runs validate_debit_credit_amounts() which asserts sum(debit) == sum(credit) for the entire GL entry set.

The GLEntry DocType also has a server-side validate hook that checks debit - credit != 0 is invalid for the same voucher+account combination.

Atomicity: All GL Entries for a voucher are inserted in a single transaction. If any entry fails, the entire set rolls back — so partial GL posting is impossible via the normal ORM path.

Bypass risk: Using frappe.db.sql() to insert directly into tabGL Entry bypasses all these checks. Always use ERPNext's make_gl_entries() for any accounting customization.

SCENARIOERPNext
Scenario: You need to add a custom workflow approval step (e.g., CFO approval) between Sales Order submission and Delivery Note creation. How do you implement this without modifying ERPNext core?
▾
Answer

Approach: Frappe Workflow + custom validation hook

1. Create a Workflow on Sales Order with states: Draft → Pending CFO Approval → Approved → Submitted. Assign transitions to roles.

2. Block Delivery Note creation unless SO is in "Approved" state — add a hook:

# hooks.py
doc_events = {
    "Delivery Note": {
        "before_insert": "myapp.validations.check_so_approval"
    }
}

# myapp/validations.py
def check_so_approval(doc, method):
    for item in doc.items:
        if item.against_sales_order:
            so = frappe.get_doc("Sales Order",
                                item.against_sales_order)
            if so.workflow_state != "Approved":
                frappe.throw(
                    f"Sales Order {so.name} not yet approved by CFO."
                )

3. Notify CFO on state change via doc_events → on_update — send email or WhatsApp notification when state changes to "Pending CFO Approval".

4. No ERPNext core modification — fully upgrade-safe.

21
COREBENCH
What exactly does bench migrate do, and what can go wrong in production during a migration with live users?
▾
Answer

bench migrate does:

1. Syncs DocType definitions → runs ALTER TABLE to add/modify/remove columns.

2. Runs unexecuted patch files in order.

3. Rebuilds search indexes and clears cache.

Production risks with live users:

1. Table locks: ALTER TABLE ADD COLUMN in MariaDB can lock the table for seconds to minutes on large tables. Users get DB errors during this window.

2. Patch failures: If a patch fails midway, future bench migrate calls will keep retrying it — blocking all subsequent patches.

3. Column removal: If a DocType field is deleted, its DB column is NOT dropped automatically (Frappe is conservative). But if you explicitly add a column deletion, you can lose data.

Best practices: Run migrations in a maintenance window. Use pt-online-schema-change for large table ALTERs. Always backup before migration. Test patches on staging first.

SCENARIOINTEGRATION
Scenario: You need to build a real-time webhook consumer that processes 200+ events/minute from a payment gateway and creates ERPNext Payment Entries. How do you architect this to be reliable and not block the web workers?
▾
Answer

Architecture:

1. Thin webhook receiver — whitelisted endpoint does only: validate HMAC signature, store raw payload in a Webhook Log DocType, return 200 immediately. Never process inline.

@frappe.whitelist(allow_guest=True)
def receive_payment_webhook():
    payload = frappe.request.data
    validate_hmac(payload)  # fail fast if invalid
    
    frappe.get_doc({
        "doctype": "Webhook Log",
        "payload": payload.decode(),
        "status": "Pending",
        "source": "PaymentGateway"
    }).insert(ignore_permissions=True)
    frappe.db.commit()
    
    # Enqueue background processing
    frappe.enqueue(
        "myapp.payments.process_webhook",
        log_name=frappe.db.get_last_created("Webhook Log"),
        queue="short"
    )
    return {"status": "ok"}

2. Background worker processes the log entry, creates Payment Entry, marks log as Processed or Failed.

3. Idempotency: Check if a Payment Entry with the same gateway transaction ID already exists before creating — handle retries from the gateway.

4. Dead-letter queue: Failed logs are retried with exponential backoff via a scheduler job.

5. Scale workers: Add more short queue workers in Procfile to handle burst load.

23
CORESECURITY
How do you implement JWT-based embedding of Frappe/Metabase dashboards securely? What are the token leakage risks?
▾
Answer

Flow: Frappe backend generates a signed JWT with user identity + dashboard ID and a short expiry (e.g., 10 min). Frontend receives this token and uses it as a URL parameter to embed the dashboard in an iframe.

import jwt, time

def get_metabase_embed_token(dashboard_id, user_email):
    secret = frappe.conf.metabase_secret_key
    payload = {
        "resource": {"dashboard": dashboard_id},
        "params": {
            "user_email": user_email  # RBAC filter
        },
        "exp": round(time.time()) + (60 * 10)  # 10 min
    }
    return jwt.encode(payload, secret, algorithm="HS256")

Token leakage risks:

1. Token in URL — appears in browser history, server access logs, and Referer headers. Mitigation: use POST to receive token, store in memory only.

2. Long expiry — a leaked token grants dashboard access until expiry. Keep expiry ≤ 10 minutes.

3. No audience binding — token doesn't bind to client IP. If stolen, it works from anywhere. Mitigate with short TTL.

4. Insecure storage — never store embed tokens in localStorage. Store in component memory (React state) only.

24
SCENARIODEBUGGING
Scenario: Production site suddenly becomes very slow — page loads take 8–10 seconds. No code changes were deployed. Walk through your triage process.
▾
Answer

Triage checklist:

1. Check Redis — redis-cli INFO memory. If used_memory near maxmemory, Redis is evicting keys or rejecting writes — cache miss storm will flood the DB.

2. Check MariaDB slow query log — enable slow_query_log if not on. Look for queries > 1s. Common culprit: a new scheduler job doing a full table scan.

3. Check worker queue depth — rq info. If queues are backed up by thousands of jobs, web requests may be waiting for Redis responses.

4. Check Gunicorn workers — ps aux | grep gunicorn. If all workers are in D-state (disk wait), likely an I/O bottleneck — check disk usage and iowait via iostat.

5. Check MariaDB connections — SHOW PROCESSLIST. If you see many "waiting for lock" or "sleeping" connections, a transaction is holding a lock (often a stalled background job).

6. Check Frappe Error Log — any recurring exceptions can trigger retry storms.

Most common root cause without code change: Data volume crossed an index cardinality threshold — a query that was fast on 10k rows is now full-scanning at 500k rows.

SCENARIOARCHITECTURE
Scenario: A client wants to expose ERPNext data to a React Native mobile app. How do you design the API layer securely and efficiently?
▾
Answer

Architecture decisions:

1. Auth: Use Frappe's built-in API key + secret (token auth) — Authorization: token api_key:api_secret. Never use session cookies from a mobile app. Create per-user API tokens.

2. Endpoint design: Don't expose raw frappe.get_list() directly. Build purpose-built whitelisted methods that return only the fields the mobile app needs — reduces payload, hides internal fields.

3. Pagination: All list endpoints must support limit + start or cursor-based pagination. Mobile apps cannot load 50k records.

4. Rate limiting: Add Nginx rate limiting per token. Frappe doesn't have built-in API rate limiting.

5. Versioning: Prefix all custom endpoints with /api/method/myapp.v1.* — makes breaking-change management easier when mobile app versions drift.

6. Caching: For read-heavy endpoints (e.g., product catalog), cache responses in Redis with a short TTL and invalidate on DocType save via doc_events → on_update.

@frappe.whitelist()
def get_dashboard_summary():
    """Mobile-optimized endpoint — returns only needed fields"""
    user = frappe.session.user
    return {
        "pending_orders": frappe.db.count("Sales Order",
            {"owner": user, "status": "Pending"}),
        "today_collections": get_today_collection(user),
    }
