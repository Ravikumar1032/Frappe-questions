Integration Patterns
Q01
SCENARIOARCHITECTURE
Design a reliable webhook consumer that processes 200+ payment events/minute and creates ERPNext Payment Entries without blocking web workers.
▾
Answer

Architecture — thin receiver + background processor:

# 1. Thin whitelisted receiver — does ONLY:
#    - Validate HMAC, store raw payload, return 200 fast
@frappe.whitelist(allow_guest=True)
def receive_payment_event():
    raw = frappe.request.data
    sig = frappe.request.headers.get("X-Signature")
    if not verify_hmac(raw, sig):
        frappe.throw("Invalid signature", frappe.AuthenticationError)

    log = frappe.get_doc({
        "doctype": "Webhook Log",
        "source": "PaymentGateway",
        "payload": raw.decode("utf-8"),
        "status": "Pending",
        "idempotency_key": frappe.request.headers.get("X-Idempotency-Key")
    }).insert(ignore_permissions=True)
    frappe.db.commit()

    frappe.enqueue(
        "myapp.payments.process_payment_event",
        log_name=log.name,
        queue="short",
        timeout=120
    )
    return {"status": "queued"}
# 2. Background processor — idempotent
def process_payment_event(log_name):
    log = frappe.get_doc("Webhook Log", log_name)
    if log.status != "Pending":
        return  # already processed (retry guard)

    payload = frappe.parse_json(log.payload)
    txn_id = payload.get("transaction_id")

    # Idempotency: check if already created
    if frappe.db.exists("Payment Entry",
                         {"custom_txn_id": txn_id}):
        log.db_set("status", "Duplicate")
        return

    try:
        create_payment_entry(payload)
        log.db_set("status", "Processed")
        frappe.db.commit()
    except Exception:
        log.db_set("status", "Failed")
        frappe.log_error(frappe.get_traceback(), log_name)
For burst traffic, add multiple short queue workers in Procfile. The receiver always returns in < 50ms — it never does heavy work.
JWT & Embed Security
Q02
CORESECURITY
How do you implement JWT-based Metabase/Superset dashboard embedding securely? What are the token leakage risks?
▾
Answer

Flow: Frappe backend generates a short-lived signed JWT. Frontend receives token and passes it as URL param to iframe src. Token is never stored persistently.

import jwt, time

@frappe.whitelist()
def get_embed_token(dashboard_id):
    user = frappe.session.user
    secret = frappe.conf.metabase_secret_key

    # RBAC: verify user has access to this dashboard
    verify_dashboard_access(user, dashboard_id)

    payload = {
        "resource": {"dashboard": int(dashboard_id)},
        "params": {
            "user_email": user,      # row-level filter in dashboard
            "company": get_user_company(user)
        },
        "exp": round(time.time()) + 600  # 10 min max
    }
    token = jwt.encode(payload, secret, algorithm="HS256")
    return token

Token leakage risks:

1. Token in URL — appears in browser history, server logs, Referer headers. Mitigation: use POST endpoint to receive token, store only in React state/memory.

2. Long expiry — leaked token works until expiry. Keep ≤ 10 minutes.

3. No audience binding — token works from any IP if stolen. Short TTL is the only mitigation in Metabase's JWT embed model.

4. Logging the token — ensure your Frappe access logs don't capture the token. Use POST, not GET, for token delivery.

Real-time & Scaling
Q03
SCENARIOSCALING
Production site is suddenly 8–10 seconds per page with no code deploy. Walk through your complete triage process.
▾
Answer

Systematic triage:

1. Check Redis: redis-cli INFO memory — if used_memory near maxmemory, Redis is evicting keys. Every cache miss hits DB directly → DB overload.

2. Check MariaDB slow queries: SHOW FULL PROCESSLIST — look for queries in 'Waiting for lock' or running > 2s. A stalled background job can hold row locks.

3. Check worker queue depth: rq info — thousands of backed-up jobs can starve Redis responses for web workers.

4. Check Gunicorn worker states: ps aux | grep gunicorn — D-state (disk wait) means I/O bottleneck. Check iostat -x 1.

5. Check Frappe Error Log: Recurring exceptions can cause retry storms that flood DB.

6. Check for table lock: SHOW ENGINE INNODB STATUS\\G — look for TRANSACTIONS section, find blocking query.

-- Find blocking queries in MariaDB
SELECT r.trx_id waiting_trx,
       r.trx_query waiting_query,
       b.trx_id blocking_trx,
       b.trx_query blocking_query
FROM information_schema.innodb_lock_waits w
JOIN information_schema.innodb_trx b ON b.trx_id = w.blocking_trx_id
JOIN information_schema.innodb_trx r ON r.trx_id = w.requesting_trx_id;
Most common root cause without a code change: data volume crossed an index cardinality threshold. A query that was fast at 10k rows is now full-scanning at 500k rows. Add the missing index and it resolves immediately.
