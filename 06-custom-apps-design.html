Custom Apps & DocType Design

Child table vs Link vs Dynamic Link, field rename migration strategy, audit trail implementation.

DocType Design Decisions
Q01
COREDESIGN
When do you use Child Table vs Link field vs Dynamic Link? What are the query and reporting trade-offs?
▾
Answer

Child Table: Multiple rows of the same structure owned by a parent. Stored in separate DB table (tabSales Invoice Item). Rows are deleted when parent is deleted. Use for line items, sub-records with multiple entries.

Link field: Foreign key to a specific DocType. Type-safe, indexable. Standard ORM filters work. Best for relationships like Invoice → Customer.

Dynamic Link: Combo of a link_doctype selector + value field. Flexible — link to any DocType. Cannot be efficiently indexed because the target table is only known at runtime.

Reporting trade-offs:

-- Link field (fast — static JOIN)
SELECT si.name, c.customer_name
FROM `tabSales Invoice` si
JOIN `tabCustomer` c ON c.name = si.customer  -- indexed

-- Dynamic Link (slow — runtime table resolution)
-- Cannot create a useful static index on the value field
-- because the table name is stored in another column
For reporting-heavy DocTypes, always prefer Link over Dynamic Link. Dynamic Links kill query performance at scale.
Migration & Patches
Q02
SCENARIOMIGRATION
You need to rename a custom field used in filters, reports, and client scripts across the app — without data loss. What is your migration strategy?
▾
Answer

NEVER rename directly in DocType JSON — it drops and recreates the column, losing all data.

Safe 5-step strategy:

1. Add new field alongside old (both exist in DocType)

2. Write a patch to copy data from old → new:

# myapp/patches/v2_0/rename_custom_field.py
def execute():
    frappe.db.sql("""
        UPDATE `tabMyDocType`
        SET new_field_name = old_field_name
        WHERE old_field_name IS NOT NULL
          AND (new_field_name IS NULL OR new_field_name = '')
    """)
    frappe.db.commit()

3. Update all references — grep codebase for old field name:

# Find all references
grep -r "old_field_name" apps/myapp/ --include="*.py"
grep -r "old_field_name" apps/myapp/ --include="*.js"
grep -r "old_field_name" apps/myapp/ --include="*.json"

4. Mark old field as hidden — deploy, monitor for one sprint

5. Delete old field in next release after confirming zero references

Add the patch to patches.txt BEFORE deploying the DocType change — data migration should run before any code tries to read the new field.
Audit Trails
Q03
COREAUDIT
How do you implement a selective field-level audit trail for sensitive data in Frappe?
▾
Answer

Built-in versioning (Track Changes on DocType) tracks all fields as JSON diffs — too noisy for compliance use cases.

Custom field-level audit trail:

# hooks.py
doc_events = {
    "Customer": {"on_update": "myapp.audit.log_changes"}
}

# myapp/audit.py
SENSITIVE_FIELDS = ["pan_number", "credit_limit", "gst_number"]

def log_changes(doc, method):
    old = doc.get_doc_before_save()
    if not old:
        return  # new record, no diff

    for field in SENSITIVE_FIELDS:
        old_val = old.get(field)
        new_val = doc.get(field)
        if str(old_val or "") != str(new_val or ""):
            frappe.get_doc({
                "doctype": "Field Audit Log",
                "reference_doctype": doc.doctype,
                "reference_name": doc.name,
                "field_name": field,
                "old_value": str(old_val or ""),
                "new_value": str(new_val or ""),
                "changed_by": frappe.session.user,
                "ip_address": frappe.local.request_ip
            }).insert(ignore_permissions=True)
Create the 'Field Audit Log' DocType with is_submittable=False and track_changes=False to avoid recursive audit loops.
