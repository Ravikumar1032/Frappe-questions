Performance & Database

N+1 queries, report optimization for 500k+ records, commit() vs savepoint() pitfalls, and index management.

N+1 Query Problems
Q01
COREPERF
What causes N+1 query problems in Frappe? How do you identify and fix them?
▾
Answer

Common N+1 patterns:

1. Calling frappe.get_doc() inside a loop over a frappe.get_list() result

2. Accessing doc.get_all_children() inside a report loop

3. Using frappe.db.get_value() inside a Jinja template loop

# WRONG — N+1 (1 query + N queries)
invoices = frappe.get_list("Sales Invoice", fields=["name"])
for inv in invoices:
    doc = frappe.get_doc("Sales Invoice", inv.name)  # N queries!
    process(doc.grand_total, doc.customer)

# CORRECT — 1 query, all needed fields
invoices = frappe.get_list("Sales Invoice",
    fields=["name", "customer", "grand_total", "status"],
    filters={"docstatus": 1}
)
for inv in invoices:
    process(inv.grand_total, inv.customer)

Identification: Enable query debug in site_config.json: "logging": 2. Check frappe.log for repeated identical queries.

For aggregations, always use frappe.db.sql() with proper JOINs — never Python-side aggregation over get_list() results.
Report & Query Optimization
Q02
SCENARIOPERF
A custom Script Report times out for clients with 500k+ records. Walk through your exact optimization approach.
▾
Answer

Step 1 — EXPLAIN the query:

EXPLAIN SELECT si.name, si.customer, si.grand_total
FROM `tabSales Invoice` si
WHERE si.posting_date >= '2024-01-01'
AND si.company = 'Acme'
-- Look for: type = ALL (full scan) → bad
-- Look for: type = ref, range → good

Step 2 — Add targeted index:

# In a patch or bench execute:
frappe.db.add_index("Sales Invoice",
    ["posting_date", "company", "docstatus"])
frappe.db.commit()

Step 3 — Switch to raw SQL for the report:

def execute(filters):
    return get_columns(), frappe.db.sql("""
        SELECT si.name, si.customer, si.grand_total,
               SUM(sii.amount) as item_total
        FROM `tabSales Invoice` si
        JOIN `tabSales Invoice Item` sii ON sii.parent = si.name
        WHERE si.posting_date BETWEEN %(from_date)s AND %(to_date)s
          AND si.docstatus = 1
        GROUP BY si.name
        LIMIT %(limit)s OFFSET %(offset)s
    """, filters, as_dict=True)

Step 4 — Async report: For very heavy reports, use Frappe's built-in background report flag — user gets notified when it's ready.

Never return all 500k rows. Always paginate with LIMIT/OFFSET or cursor-based pagination in reports.
Transaction Safety
Q03
DANGERCORE
Explain frappe.db.commit() vs frappe.db.savepoint(). When does commit inside a loop cause a production disaster?
▾
Answer

frappe.db.commit() — flushes the entire transaction. All pending writes are permanent. Releases all row locks.

frappe.db.savepoint(name) — creates a rollback point within the current transaction. Failure after this can roll back to here without losing earlier work in the same transaction.

Disaster scenario: Processing 1,000 invoices with commit() after each. Job crashes at invoice 601:

→ Invoices 1–600: permanently committed ✓

→ Invoices 601–1000: never written ✗

→ Data in inconsistent half-processed state with no clean rollback path

Safe pattern with savepoints:

failed = []
for i, row in enumerate(records):
    sp = f"sp_{i}"
    try:
        frappe.db.savepoint(sp)
        create_invoice(row)
    except Exception as e:
        frappe.db.rollback(save_point=sp)
        failed.append({"row": i, "error": str(e)})

frappe.db.commit()  # single commit at end
report_failures(failed)
This is a top interview trap. Commit-in-loop is one of the most common production data integrity bugs in Frappe apps.
Q04
COREPERF
How do you add and manage custom database indexes in Frappe without modifying ERPNext source?
▾
Answer

Method 1 — DocType field flag: For simple single-column indexes, enable 'Search Index' on the field in the DocType form. Frappe adds the index on next bench migrate.

Method 2 — Patch file for composite indexes:

# myapp/patches/v1_0/add_invoice_index.py
def execute():
    # Composite index for common filter pattern
    if not frappe.db.has_index("tabSales Invoice",
                                "posting_date_company_idx"):
        frappe.db.add_index("Sales Invoice",
            ["posting_date", "company", "docstatus"],
            index_name="posting_date_company_idx")

Method 3 — Direct SQL for expression indexes (MariaDB 10.5+):

frappe.db.sql("""
    CREATE INDEX IF NOT EXISTS custom_lower_email_idx
    ON `tabContact` ((LOWER(email_id)))
""")
Always check frappe.db.has_index() before adding to make patches idempotent — re-running a patch that adds a duplicate index will error.
