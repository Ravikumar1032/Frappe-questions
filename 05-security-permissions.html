Security & Permissions

Role vs User vs SQL-level permissions, multi-company data leakage, and securing whitelisted endpoints.

Permission Layers
Q01
COREPERMISSIONS
Explain the three layers of Frappe permissions: Role Permissions, User Permissions, and Permission Query Conditions. Which is enforced at SQL level?
▾
Answer

Role Permissions (DocPerm): Coarse-grained CRUD access at DocType level for a Role. 'Sales User can Read+Write Sales Order.' Checked in Python before any DB call.

User Permissions: Row-level restrictions. 'User X can only see records where Company = Acme.' Stored in tabUser Permission. Frappe filters list views and get_doc calls based on these.

Permission Query Conditions: A Python function in hooks.py that dynamically appends a WHERE clause to every query for a DocType. This is the only layer enforced at SQL level.

# hooks.py
permission_query_conditions = {
    "Sales Order": "myapp.permissions.get_so_query_condition"
}

# myapp/permissions.py
def get_so_query_condition(user):
    if not user: user = frappe.session.user
    if "Sales Manager" in frappe.get_roles(user):
        return ""  # no restriction
    # Injected directly into WHERE clause of every SELECT
    return f"(`tabSales Order`.owner = '{frappe.db.escape(user)}')"

Key distinction: User Permissions are Python-evaluated and can be accidentally bypassed by raw frappe.db.sql() without explicit filters. Permission Query Conditions are injected into all ORM-generated queries — much harder to bypass.

Always escape user input in permission_query_conditions using frappe.db.escape() to prevent SQL injection.
Security Vulnerabilities & Fixes
Q02
SCENARIOSECURITY
A whitelisted API endpoint is leaking data from other companies in a multi-company setup. What went wrong and how do you fix it?
▾
Answer

What went wrong:

1. The @frappe.whitelist() function uses frappe.db.sql() or frappe.db.get_all() without a company filter — bypassing User Permissions entirely.

2. No has_permission() call on returned documents.

Secure fix:

@frappe.whitelist()
def get_my_invoices(company=None):
    user = frappe.session.user

    # 1. Get user's allowed companies from User Permissions
    allowed = [p.for_value for p in frappe.get_all(
        "User Permission",
        filters={"user": user, "allow": "Company"},
        fields=["for_value"],
        ignore_permissions=True
    )]

    if not allowed:
        frappe.throw("No company access", frappe.PermissionError)

    # 2. If company param given, verify user has access to it
    if company and company not in allowed:
        frappe.throw("Access denied", frappe.PermissionError)

    filters = {"company": ["in", allowed], "docstatus": 1}
    if company:
        filters["company"] = company

    return frappe.get_list("Sales Invoice",
        filters=filters,
        fields=["name", "customer", "grand_total"]
    )
Never return raw DB results from a whitelisted method without explicit company/owner scoping. Treat every whitelist endpoint as a public API endpoint.
Q03
CORESECURITY
What is the difference between @frappe.whitelist() and @frappe.whitelist(allow_guest=True)? What are the risks of each?
▾
Answer

@frappe.whitelist() — callable by any logged-in user. Frappe validates session cookie or API key. If called without auth, returns 403.

@frappe.whitelist(allow_guest=True) — callable by unauthenticated users. frappe.session.user will be Guest. Exposed publicly — accessible via curl with no credentials.

Risks of allow_guest:

1. No rate limiting by default — vulnerable to scraping and brute-force

2. If you accidentally call frappe.get_list() without filters, you expose all records

3. No audit trail — all calls appear as 'Guest' in logs

Securing allow_guest endpoints:

@frappe.whitelist(allow_guest=True)
def public_product_catalog():
    # Only return explicitly public data
    return frappe.get_list("Item",
        filters={"show_in_website": 1, "disabled": 0},
        fields=["item_name", "website_image", "web_long_description"],
        limit=50  # always limit guest endpoints
    )
Never use allow_guest=True for endpoints that read user-specific, financial, or PII data.
