Deployment & DevOps

bench migrate risks, zero-downtime deploy patterns, Supervisor config, and production monitoring.

bench migrate Risks
Q01
DANGERCORE
What exactly does bench migrate do, and what can go wrong in production during a live migration?
▾
Answer

bench migrate does:

1. Syncs DocType JSON → runs ALTER TABLE to add/modify columns

2. Runs unexecuted patch files in order from patches.txt

3. Rebuilds search indexes, clears cache, rebuilds website routes

Production risks with live users:

1. Table locks: ALTER TABLE ADD COLUMN in MariaDB locks the table during the operation — seconds to minutes for large tables. Users get DB errors.

2. Patch failures: If a patch fails midway, all subsequent patches are blocked until the failed patch is fixed or skipped.

3. Long migration: Migrations on a busy system can take 30+ minutes — during this time, the site may serve partially migrated data if old workers are still running.

Safe migration playbook:

# 1. Enable maintenance mode
bench set-maintenance-mode on

# 2. Take DB backup
bench backup --with-files

# 3. Run migration
bench migrate

# 4. Restart all workers
bench restart

# 5. Disable maintenance mode
bench set-maintenance-mode off

For large tables (> 1M rows), use pt-online-schema-change from Percona Toolkit to run schema changes without locking.

Zero-downtime Deploys
Q02
SCENARIODEVOPS
How do you achieve zero-downtime deployment of a Frappe app update that includes a DB schema change?
▾
Answer

The challenge: You cannot apply a schema change and deploy new code atomically — there's always a window where old code runs against new schema or vice versa.

Expand-Contract pattern:

1. Expand phase: Add new column/field (old code ignores it, new code uses it). Deploy this first.

2. Migrate phase: Run bench migrate to apply schema. Old code still works (new column is nullable/has default).

3. Contract phase: Deploy new code that reads the new field. Remove old field in a later release.

Nginx/Gunicorn rolling restart:

# Graceful reload — Gunicorn finishes in-flight requests
# before reloading workers (no new connection drops)
supervisorctl signal HUP frappe-web

# Or via bench:
bench restart  # sends SIGHUP to gunicorn
Never deploy code and schema together if the change is breaking. Always use expand-contract with at least one release cycle between phases.
Monitoring & Observability
Q03
COREMONITORING
How do you set up production monitoring for a Frappe site? What are the key metrics to watch?
▾
Answer

Key metrics to monitor:

1. Gunicorn worker saturation: If all workers are busy, new requests queue. Alert when > 80% workers busy for > 30s

2. Redis memory: Alert at 80% of maxmemory. Redis OOM causes cache misses that cascade to DB overload

3. RQ queue depth: Alert when default or short queue exceeds 100 pending jobs

4. MariaDB slow queries: Alert on queries > 2s. Enable slow_query_log in MariaDB config

5. Frappe Error Log count: Alert when new errors spike in a 5-minute window

# Expose Frappe Error Log count via a custom health endpoint
@frappe.whitelist(allow_guest=True)
def health_check():
    return {
        "status": "ok",
        "error_log_last_hour": frappe.db.count(
            "Error Log",
            {"creation": [">", frappe.utils.add_to_date(None, hours=-1)]}
        ),
        "rq_pending": get_rq_pending_count()
    }

Use Zabbix or Prometheus + Grafana for time-series monitoring. Frappe has a built-in /api/method/frappe.monitor.get_all_jobs endpoint for RQ inspection.
