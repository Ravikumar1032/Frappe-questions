Scheduler & Workers

RQ scheduler internals, concurrent job prevention, silent failure debugging, and queue selection strategy.

Scheduler Internals
Q01
CORESCHEDULER
How does Frappe's scheduler work internally? How do you prevent concurrent execution of the same job?
▾
Answer

Internals: Frappe uses rq-scheduler — a cron-like scheduler that enqueues jobs into Redis queues at configured intervals. The beat process (bench schedule) is the cron tick. RQ workers consume from named queues (default, short, long).

Concurrency problem: If a scheduled job runs longer than its interval, RQ enqueues it again while the previous is still running — causing concurrent execution and potential data corruption.

Solution — Redis lock pattern:

def my_scheduled_job():
    lock_key = "frappe_lock:my_job"
    # Atomic: set only if not exists, expire in 10 min
    acquired = frappe.cache().set_value(
        lock_key, 1, expires_in_sec=600
    )
    if not acquired:
        frappe.logger().info("my_job already running, skipping")
        return
    try:
        process_records()
        frappe.db.commit()
    except Exception:
        frappe.log_error(frappe.get_traceback(), "my_job error")
    finally:
        frappe.cache().delete_key(lock_key)
frappe.cache().set_value() is NOT atomic SET NX. For true distributed locks use frappe.cache().redis_client.set(key, 1, nx=True, ex=600) directly.
Background Job Failures
Q02
SCENARIOWORKERS
frappe.enqueue() jobs are silently failing in production. Workers show as healthy. How do you trace and fix?
▾
Answer

Common silent failure causes:

1. Job timeout: Default RQ timeout is 300s. Jobs exceeding this are killed silently. Fix: frappe.enqueue(..., timeout=3600)

2. Queue name mismatch: Job enqueued to long queue but no worker listens on long. Check Procfile — ensure worker_long process is defined and running.

3. Redis memory full: Jobs are dropped. Monitor: redis-cli INFO memory

4. Swallowed exception: Job function has bare except: pass. Check worker logs: bench logs worker

Inspection commands:

# Check queued/failed jobs
bench execute frappe.utils.background_jobs.get_jobs

# Direct RQ inspection
rq info --url redis://localhost:11000

# View failed job details
rq failed --url redis://localhost:11000

Best practice — always wrap job logic:

def my_job(doc_name):
    try:
        doc = frappe.get_doc("MyDocType", doc_name)
        do_work(doc)
        frappe.db.commit()
    except Exception:
        frappe.log_error(frappe.get_traceback(),
                         f"my_job failed for {doc_name}")
Q03
COREQUEUES
What is the difference between the default, short, and long RQ queues in Frappe? How do you choose?
▾
Answer

Three named queues:

• default — general purpose async tasks, medium duration (< 5 min)

• short — quick tasks that need fast pickup (< 1 min). E.g., sending a single email, webhook acknowledgment.

• long — heavy processing (> 5 min). E.g., bulk data migration, large report generation, file processing.

Worker configuration in Procfile:

# Procfile
worker_short: bench worker --queue short
worker_default: bench worker --queue default,short
worker_long: bench worker --queue long,default,short

Choosing: Always match job duration to queue. If your long job runs on the short queue, it blocks quick jobs behind it — notifications get delayed for minutes.

In high-traffic setups, run multiple short queue workers: worker_s1, worker_s2 each consuming from short queue only.
