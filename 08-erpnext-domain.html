Accounting Internals
Q01
COREACCOUNTING
How does ERPNext enforce double-entry accounting at code level? What prevents an imbalanced GL Entry?
▾
Answer

Mechanism: ERPNext calls make_gl_entries() in the accounting controller. This generates a list of GL Entry dicts. Before inserting, validate_debit_credit_amounts() asserts sum(debit) == sum(credit) for the entire set.

GLEntry DocType validation: The GLEntry controller's validate hook also checks each individual entry — debit or credit must be > 0, not both.

Atomicity: All GL Entries for a voucher are inserted inside one transaction. If any entry fails, the full set rolls back — partial GL posting is impossible via ORM.

Bypass risk: Direct frappe.db.sql(INSERT INTO tabGL Entry ...) bypasses all checks. Never do this. Always use ERPNext's make_gl_entries() for any accounting customization.

# Correct way to post custom GL entries
from erpnext.accounts.general_ledger import make_gl_entries

gl_entries = [
    self.get_gl_dict({
        "account": self.debit_account,
        "debit": self.amount,
        "credit": 0,
        "against": self.credit_account,
    }),
    self.get_gl_dict({
        "account": self.credit_account,
        "debit": 0,
        "credit": self.amount,
        "against": self.debit_account,
    }),
]
make_gl_entries(gl_entries)
Workflow & Process Customization
Q02
SCENARIOWORKFLOW
How do you add a CFO approval step between Sales Order submission and Delivery Note creation without modifying ERPNext core?
▾
Answer

Approach: Frappe Workflow + validation hook

1. Create a Workflow on Sales Order with states: Draft → Pending CFO Approval → Approved → Submitted

2. Block Delivery Note creation until SO is Approved:

# hooks.py
doc_events = {
    "Delivery Note": {
        "before_insert": "myapp.validations.check_so_cfo_approval"
    }
}

# myapp/validations.py
def check_so_cfo_approval(doc, method):
    for item in doc.items:
        if not item.against_sales_order:
            continue
        so = frappe.get_cached_doc("Sales Order",
                                    item.against_sales_order)
        if so.workflow_state != "Approved":
            frappe.throw(
                f"Sales Order {so.name} is pending CFO approval. "
                f"Delivery cannot be created.",
                frappe.PermissionError
            )

3. Notify CFO when state changes to 'Pending CFO Approval':

doc_events = {
    "Sales Order": {
        "on_update": "myapp.notifications.notify_cfo_if_pending"
    }
}

def notify_cfo_if_pending(doc, method):
    if (doc.workflow_state == "Pending CFO Approval" and
        doc.get_doc_before_save().workflow_state != "Pending CFO Approval"):
        frappe.sendmail(
            recipients=get_cfo_emails(),
            subject=f"SO {doc.name} awaiting your approval",
            message=f"Amount: {doc.grand_total}"
        )
This approach is 100% upgrade-safe — zero ERPNext source modifications.
Stock & Inventory
Q03
CORESTOCK
What is the difference between FIFO, Moving Average, and LIFO stock valuation in ERPNext? When does each cause issues in practice?
▾
Answer

FIFO (First In First Out): Cost of goods sold = cost of oldest purchased stock. Valuation is accurate but recalculates stock ledger on every backdated entry — expensive computationally.

Moving Average: Running average of purchase costs. Simple, fast. Can drift from actual cost when prices fluctuate rapidly. Issues: reposting is simpler but average becomes 'polluted' after high-cost emergency purchases.

LIFO: Not supported by ERPNext (illegal in many countries under IFRS/Ind AS). Attempting to implement it requires overriding stock ledger logic — not recommended.

Practical issue with FIFO: Backdated stock entries trigger a 'repost item valuation' background job that recalculates all subsequent SLE entries. For items with thousands of transactions, this can lock the stock ledger for minutes.

Practical issue with Moving Average: Returns generate issues if the return rate doesn't match the current average — causes valuation discrepancy that Finance teams notice at period close.

For high-volume items, Moving Average is faster but FIFO is more accurate. Choose based on your client's accounting requirements, not performance preference.
