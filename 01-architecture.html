Architecture & Internals

Deep internals of request lifecycle, ORM caching, connection management, and multi-tenancy in Frappe.

Request Lifecycle
Q01
CORELIFECYCLE
Explain Frappe's full request lifecycle — from HTTP request to Python response. Where do ORM, permission check, and controller hooks fit?
▾
Answer

Full path: Nginx → Gunicorn (WSGI) → frappe.app → frappe.handler.handle() → method routing → ORM → MariaDB → response.

Permission check fires inside frappe.get_doc() before data is returned, via has_permission() which reads DocPerm + User Permission records from the DB.

Controller hooks (validate, before_save, on_submit) fire within the same DB transaction. Raising an exception triggers a full rollback.

Key insight: Frappe holds a single MariaDB connection per request (stored in frappe.db). Long-running hooks hold locks — a common production bottleneck.

Mention RQ workers for async jobs — background tasks bypass this lifecycle entirely via Redis queues and Gunicorn never touches them.
Q02
COREORM
What is the difference between frappe.get_doc(), frappe.get_cached_doc(), and frappe.get_last_doc()? When does each cause a bug?
▾
Answer

get_doc() — always queries the DB. Fresh data. Slightly slower but safe.

get_cached_doc() — reads from Redis cache first. Dangerous if a background job mutates a setting and then calls this — it gets stale config for up to cache TTL (default ~10 min).

get_last_doc() — fetches newest record by creation DESC. In high-concurrency scenarios (bulk onboarding), you may read another user's just-created record.

Production bug scenario: A scheduler job uses get_cached_doc on a System Settings DocType. Admin changes the email config. Job sends 10,000 emails to the old address for 10 minutes.

Always call frappe.clear_cache(doctype, name) after programmatic updates to single-record settings DocTypes.
Connection & Transaction Management
Q03
COREDB
How does Frappe manage DB connections per request? What happens if a background job crashes mid-transaction?
▾
Answer

Per-request connection: Frappe opens one MariaDB connection at request start (frappe.connect()), stores it as frappe.db. All ORM calls within that request use this single connection.

Auto-commit: Web requests auto-commit at the end via frappe.db.commit() in the WSGI teardown, unless an exception occurred — in which case it auto-rollbacks.

Background job crash: RQ workers catch exceptions and mark the job as Failed in Redis. The MariaDB connection is closed, triggering an implicit rollback of any uncommitted writes. No partial data survives.

Critical gotcha: If you call frappe.db.commit() inside a loop within a job, and the job crashes after iteration 500 of 1000 — iterations 1-500 are permanently committed, 501-1000 are lost. Your data is now inconsistent.

Never commit() inside a loop unless you explicitly want partial commit semantics and have idempotency guarantees.
Multi-tenancy
Q04
COREMULTI-TENANCY
How does Frappe's bench multi-site architecture work at the DB and file level? How do you share data across sites?
▾
Answer

Site isolation: Each site has its own MariaDB database, own site_config.json, and own private//public/ file directories under sites/sitename/.

Redis sharing: Redis is shared across sites but all cache keys are namespaced with the site name — so cache isolation is logical, not physical.

Cross-site data options:

1. Frappe REST API — sites call each other via HTTP + API token. Simple but adds network latency.

2. Shared MariaDB views — read-only DB user with SELECT on another site's DB. Fast but bypasses all Frappe ORM, permissions, and validation.

3. Redis pub/sub — site A publishes events, site B's worker subscribes. Best for async sync. Decoupled and scalable.

For production cross-site sync, use the Frappe REST API with retry logic. Direct DB cross-reads should be last resort — they break upgrade safety.
